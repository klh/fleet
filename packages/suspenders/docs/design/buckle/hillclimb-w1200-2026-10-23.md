## Harness

  in-window policy requests **with attempt chains** (24,377 of 24,377+)
  plus their `route_attempt` chains; walks each chain under candidate
  knobs: per-row attempt budget = `num_retries + 1` (excess cut), a benched

## Objective and noise floor

- Objective (cost-fallback doctrine): **success floor first** (a keep
  never drops success by >0.5pp on either window), **then cost** =
  429-burn count + failed-request count × 64,003 tokens, **then
  latency** (p50/p95 recorded per round in the JSON artifact, never
  traded for cost).
- Cost is priced per-request and compared **paired per request**
  (cand − base on the same rid), bootstrap-resampled 300× (seeded LCG,
  seed = round index) → CI95. Keep requires CI95 hi < 0 on BOTH windows.
- Noise floor: baseline config replayed twice → byte-identical outcomes
  (determinism pass). Noise half-width = the CI95 half-width of the
  raw-vs-sim delta ≈ **193 cost units**; the smallest accepted
  improvement (R6 train mean −1,085) clears it ~6×.

  1,097→1,368) — the cost objective still improves because failed

## Declared assumptions

1. Logged attempt outcomes are valid counterfactual samples (no
   second-order interference between concurrent requests).
2. Streaming/non-streaming is not distinguishable per ledger row, so the
   timeout knobs are out of scope; only the three retry/cooldown knobs
   carry ledger-visible signal. `retry_after_cap_s` also skipped
   (`retry_after_ms` mostly null in the window).
3. A failed request is priced at the TRAIN mean tokens per success
   (64,003); a 429 burns 1 unit. Alternative pricings shift absolute
   cost but not the R1–R4 floor verdicts; R6's keep is robust while
   failed-request pricing stays ≫ burn units.
4. TEST discipline is same-session: the optimizer evaluates both windows
   per round; TEST was not used to select the next knob (agenda was
   fixed before R1).
