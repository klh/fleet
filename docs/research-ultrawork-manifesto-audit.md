# Adversarial audit: oh-my-opencode ultrawork manifesto

Audited 2026-10-07. Repo: `opensoft/oh-my-opencode` (branch `dev`, default `master`). Manifesto:
`docs/ultrawork-manifesto.md`. Method: every manifesto claim checked against actual source in the
repo — file paths cited below are real files read during this audit. Prompt text counts as
**prompt posture** (model-advised, no enforcement), never as a mechanism.

Owner framing held throughout: this may be "LLM shit thought without thought" — the audit's job was
to separate mechanism from manifesto vibes. Bottom line up front: **the continuation machinery is
real and is the best thing in the repo; the philosophy chapters are largely vaporware.**

## Verdict

### Real mechanisms worth lifting

1. **Todo continuation enforcer** (`todo-continuation-enforcer.ts`) — the strongest artifact in the
   repo. Event-driven (`session.idle` ≈ Claude Code Stop), state-checked (real todo API, not prose),
   re-prompts with a system directive. Its value is mostly in the **guards**: abort window (3 s),
   user-message grace period, tool-activity cancellation, skip-agent list, write-permission check,
   background-task interlock. Directly validates **W502**.
2. **Ralph loop completion sentinel** (`ralph-loop/index.ts`) — the anti-"I'm done lies" claim is
   actually TWO mechanisms: todo-state re-check (above) plus a machine-checkable completion
   sentinel (`<promise>DONE</promise>`), with a hard iteration cap (default 100) and persisted
   state. Trusting a verifiable sentinel over prose completion is the transferable idea.
3. **Category model routing** (`model-requirements.ts` + `model-resolver.ts`) — hand-authored
   per-agent/per-category fallback ladders with live availability checking. Fleet already has this
   shape (`routing-policy.yaml`); nothing new to lift, but it independently confirms the design.
4. **BackgroundManager** (`background-agent/manager.ts`) — concurrency-keyed queue per model/agent,
   stale reaping with abort, todo-aware completion, parent notification by injection. The
   **concurrency-key** idea (one slot per model, queue the rest) is worth stealing for dispatch.
5. **start-work resume** (`start-work/index.ts`) — file-state (boulder.json + markdown checkbox
   parsing) driving session resume. Crude vs the work graph, but the "resume = re-inject first
   unchecked item" pattern is clean.

### Vaporware

"Human intervention = failure signal" (no instrumentation, and aborts are respected, not recorded as
failures) · "indistinguishable code" (posture) · 10x/20x/100x and 70% token-savings numbers
(unmeasured) · "Wisdom accumulation" (plan-scoped notepads at best) · "predictable like a compiler"
(nothing deterministic) · escalation discipline (prompt-only, unenforced) · "prompt engineering is
obsolete" (the repo is prompt engineering).

### Ruling on W502 / W503

- **W502 (Stop-gate continuation enforcer): JUSTIFIED.** omO ships a production implementation of
  exactly this; the manifesto claim is backed by ~460 lines of guarded code plus tests. Port with
  their guard set (abort window, user grace, tool-activity cancel, skip-agents) and consider adding
  the ralph-loop completion sentinel as a second, verifiable done-gate.
- **W503 (keyword fan-out posture): WEAKLY JUSTIFIED — re-scope.** In omO, keywords select
  **prompts**, not machinery: the detector is a regex that prepends posture text and sets a
  reasoning-effort variant. Fan-out itself is agent-initiated through `delegate_task` +
  BackgroundManager concurrency keys. If fleet wants keyword-triggered fan-out as a hard mechanism,
  that goes beyond omO — the honest lift is (a) regex keyword → injected posture prompt, and
  (b) concurrency-keyed lanes, not "keyword spawns the fleet."
