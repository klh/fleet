# W1124.18.2 — Plan: capability-advertised execution and oversight on autonomous hubs

Phase 2 of the owner sequence in W1124.18. Phase 1 (W1124.18.1) proved the
sustained40 milestone gate and planned the self-healing supervisor; its R1
control lease is the prerequisite this plan builds on. Planning only — no
controller code lands from this item. Implementation is gated behind the
sustained40 milestone and a reviewed plan (this document is the plan; review
rides the existing `decision work.review` receipt plane). Offline reconnect
sync is W1124.18.3's scope; this plan states only the invariants 18.3 must
honor.

Gap analysis against the mission verbs:

- **SUPPORTS is implied, never advertised.** The manifest's `capabilities`
  block is W165 install-profile booleans (identity/issuance/admin) — not
  execution capability. No version field, no evidence, no drill, no expiry.
  The W918 catalog proves the honesty pattern for executors but is scoped to
  agent targets on one machine, not hubs.
- **Placement is not a scheduler input.** `work-alloc` scores lanes from one
  host's `.fleet/lanes.json`; there is no hub axis, no cross-host lane
  registry, and dispatch (the `dispatch` controller class) is Mac-resident.
- **No end-to-end hub-run acceptance.** Hubs serve gateways/store/board, but
  work items are claimed, executed, proven, and merged from the developer
  machine. Proof inputs (worktrees, transcripts) are dev-machine-local.
- **Partition policy is implicit.** controller-fence enforces single-writer
  per project only where it can prove liveness (same machine). Cross-host the
  fence stands down to standby — safe, but the policy ("who may mutate the
  graph while partitioned") is undocumented and undiscoverable by placement.

## 2. Requirements → design

Mission verbs mapped to one mechanism each. Reuse law (inherited from
18.1): zero new daemons, zero new transports. Every mechanism lands in an
existing lib, the fleet-loop task registry, an existing verb, or the
manifest already pulled today.

### R1 — hub SUPPORTS: versioned, evidence-backed, tested

One JSON schema, one lib (`hooks/lib/hub-supports.ts`), one producer (the
hub's own capability probe), one consumer (placement). Schema:

```json
{
  "supports_version": 1,
  "hub": "<label>",
  "generation": "<harness-receipt revision>",
  "evidence_at": "<ISO-8601>",
  "supports": {
    "executor.claude-code": { "state": "tested", "evidence": "drill:executor:claude-code passed <sha>", "tested_at": "<ISO>" },
    "executor.codex": { "state": "probed", "evidence": "bin probe only", "tested_at": null },
    "harness": { "state": "tested", "evidence": "drill:harness gate-denial proof" },
    "review": { "state": "tested", "evidence": "drill:review oracle round-trip" },
    "manifestpull": { "state": "tested", "evidence": "drill:manifestpull last-known write" },
    "merge": { "state": "tested", "evidence": "drill:merge ladder into throwaway ref" },
    "store": { "state": "tested", "evidence": "drill:store CAS round-trip on temp row" },
    "routes": { "groups": ["glm-5.3-flash", "claude-sonnet-5"], "evidence": "entitlements + assessBuckleRoute" },
    "resources": { "lane_slots": 8, "mem_gb": 64, "disk_gb": 400 },
    "policy": { "governance": "strict", "scrub": true, "egress": "singbox" }
  }
}
```

The executor/harness/review/merge/store axes use three evidence states,
borrowing W918's honesty law (detection is not runnable evidence):

- `unproven` — no drill has passed on this generation. Placement MUST NOT
  place work requiring it (fail-closed, mirroring controller-fence's refusal
  on unknown liveness).
- `probed` — cheap non-executing check passed (bin probe, route audit,
  store ping). Advisory only; never placement-sufficient alone.
- `tested` — the capability's drill passed on this generation inside its
  TTL. The only placement-sufficient state.

Routes/resources/policy stay descriptive (not states): placement joins them
as constraints, not evidence. `supports_version` bumps on schema change;
unknown versions read as `unproven` (fail-safe).

### R1b — the capability drill registry (the "tested" in SUPPORTS)

`deploy/capability-drills.ts`: one drill per capability, sandboxed, each
returning a typed receipt (cap, pass, ms, evidence sha):

- `executor.<target>`: spawn ONE bounded hello-lane on a sandboxed item in a
  temp project that must reach `work done` with the full done-gate intact.
  Expensive → runs on its own cadence, results stamped per generation.
- `harness`: a probe edit that the hook gates MUST deny (gate denial IS the
  pass evidence — the fence proves itself).
- `review`: one pinned oracle-leg round-trip (`oracle review --in` a fixture).
- `merge`: a scratch branch through the merge ladder into a throwaway ref,
  then reaped.
- `store`: CAS write+read on a temp project row in the hub's governor.db.
- `manifestpull`: a last-known write + degraded read on a capped-stream fetch.

The test suite (`test/hub-capabilities.test.ts`) runs the registry against a
sandbox store in /tmp — the drills ARE the tests. Installed hubs run due
drills via ONE fleet-loop maintenance task (`capability-probe`), stamped with
the existing maintenance-stamp idiom (attempt-stamped, nice, timeoutMs, test
clock injected). Evidence expires: each cap carries a TTL; past TTL the
state reads `unproven` at placement time even if the last drill passed
(stale evidence is not evidence). The drill receipts are artifacts (R4).

### R2 — placement + dispatch: ONE scheduler, durable authority

Placement is not a new service. `work-alloc.ts` gains a placement axis:

- `AllocLane` gains `hub` + `place` (host) fields; the source of lanes grows
  from `.fleet/lanes.json` to the store's session rows (hub sessions register
  there today via coord bootstrap) ∪ the local registry — the union is
  deduped by sid. Item `requires` caps join against `hub.supports` via the
  same `requires ⊆ caps` predicate, so a `requires: hub.merge` item places
  only where the merge drill is `tested` and fresh.
- Placement decisions are durable rows (`placements` table, store migration):
  `(item, hub, host, worktree, epoch, expires_at)` written transactionally
  WITH the claim CAS — claim and placement mint together, one tx, one truth.
- Dispatch (what/who) and placement (where) stay ONE `planAllocation` call.
  The scheduler runs ONLY where the project's scheduler authority lives (R3);
  a non-authoritative `work allocate` renders the plan read-only (today's
  no-`--apply` shape).

### R3 — durable authority, lease fencing, scoped credentials

Authority over a project's graph is lease-bounded, movable, never duplicated:

- The scheduler authority IS the `dispatch` controller class from 18.1's R1,
  held under controller-fence W576.5 (nonce/pid/birth/generation). The
  authoritative party is the hub whose fleet-loop holds the lease; handoff
  verbs (`requestControllerHandoff` → released → assumed) move authority
  between hosts, each handoff bumping the epoch. This closes 18.1's open
  decision 2: in the hub phase, `dispatch` moves to the hub; the Mac becomes
  an optional client, not a resident controller.
- Every placement/claim/close mutation carries the authority's epoch; a
  superseded authority's writes CAS-reject (the W643 stale-token law
  generalizes: token = epoch + claim nonce). Rejections are events, never
  crashes; a rejected stale authority stands down.
- Fail-closed law inherited verbatim: store unreachable = no mutation, no
  placement, no dispatch. Partitioned parties keep read-only last-known
  state and may run LOCAL lanes on their own claims, but cannot mint new
  claims, place work, or merge while partitioned.
- Credentials: lanes ride per-lane `bksk_` keys minted by the hub's belt
  admin (exists today, scoped `buckle:proxy:WRITE_`), revoked on close/test
  rule. Git push credentials are per-hub SSH deploy keys (NOT per-lane —
  lanes never hold origin credentials); scrub gate enforced at the push gate
  regardless of which host pushes.

### R4 — end-to-end hub-run work: the acceptance scenario

The DONE definition, as a specified sequence (the executable drill in §5
step 8 proves it on a sandbox hub):

1. Dev machine OFF. The hub's fleet-loop holds all five controller classes
   (dispatch/merge/maintenance/watchdog/recovery) for the project.
2. Mint: `work add` lands on the hub store (store ports already serve hubs).
3. Allocate+dispatch: the hub scheduler scores READY × registered lanes, the
   placement row + claim mint in one tx, the hub dispatch spawns the lane ON
   the hub host with its per-lane `bksk_` key, per-lane settings file, and a
   `work take`-minted worktree on the hub checkout.
4. The lane rides the hub buckle front `/w/<sid>`; W776 attribution rows land
   in the hub router ledger; the hub's git origin stays GitHub (push via hub
   deploy key, scrub gate on).
5. Close: `work done` runs hub-side against the hub store — same gates
   (claim-check, tokens, marker scan, patch-first), same proof: work.done
   event + attribution + claim-check pass.
6. Artifacts: git objects (commits, capsules, drill receipts as committed
   proof) push with the branch; bounded blobs (drill outputs, logs) land in a
   store artifact surface (size-capped, retention-bounded) — never the
   worktree, never unbounded.
7. Reviewed publication: review receipt via the `decision work.review`
   receipt plane; the merge ladder merges verified-only ancestry into main
   hub-side. Publication needs NO dev machine input.
8. Reconnect: the dev machine rejoins as a client; its pending state is
   read-only replay against the authoritative graph (idempotent by event id
   and CAS tokens — the invariant W1124.18.3 must honor).

### R5 — enterprise pin/deploy/health parity

- **Pin**: `supports.generation` must match the hub's deployed fleet pin
  (`version:` → the ref hubctl pulls). A generation mismatch with the
  project's expected pin yields authority (18.1's version ratchet) and
  expires executor/harness evidence to `unproven` — capabilities are
  generation-scoped because they are tested against a payload.
- **Deploy parity**: enterprise uses the identical install path
  (`install.sh --hub <name>` / `hubctl deploy`); SUPPORTS rendering is part
  of `hubctl status` output so an enterprise operator sees the same
  capability truth a placement decision sees.
- **Health parity**: the capability-probe maintenance task's verdict is
  served by the hub's probe sidecar (outside-process law: the fleet-loop
  cannot paint its own capabilities healthy — the sidecar re-derives the
  verdict from drill receipts and serves it on `/healthz`). Stale receipts
  = degraded verdict, honoring the health-status-contract's degrade/down
  transitions.

### R6 — secure remote git/worktree lifecycle

- Worktrees on a hub are minted ONLY by `work take` against the hub store
  (the location-vs-claim gate binds edits to that tree, same as today);
  `git status` evidence flows into liveness exactly as the stall-watch join
  reads it today.
- Origin transport: SSH deploy key scoped per hub, least scope (one key per
  hub, not per lane), stored 0600 machine-local; hub containers keep mounting
  git-pulled volumes (no host-path deploys).
- Scrub gate on every push path from any host; the deny-with-redaction
  behavior is host-independent (the gate runs in-repo via core.hooksPath).
- Lifecycle end: rogue-reap's stale-tree + serve-process reaping runs
  hub-side under the hub's `maintenance` class, honoring the
  `rogue-reap-paused` pause flag; worktree removal only after close + merge
  + review receipt (same re-integration discipline as W24844's
  re-integration items).

## 3. Partition policy — single authoritative hub vs federated coordinators

The explicit comparison the mission demands. Terminology: the **smallest
reliable partition** is the minimal set of parties whose simultaneous
operation is required for the project to make forward progress.

| Property                    | A: single authoritative hub (movable)                | B: federated coordinators (any hub mutates)       | C: static sharding (fixed binding)            |
| --------------------------- | ---------------------------------------------------- | ------------------------------------------------- | --------------------------------------------- |
| Smallest reliable partition | {the authoritative hub}                              | {any hub} — progress during partitions            | {its shard's hub}                             |
| Offline multiwriter         | Structurally impossible (epoch CAS rejects)          | Possible by design; needs semantic merge          | Impossible per shard, but binding is unmovable|
| Partition behavior          | Non-authoritative party degrades to read-only client | Both sides keep mutating; heal = conflict surgery | Orphaned shard while its hub is down          |
| New machinery               | Handoff verbs (exist), epoch CAS (exists)            | CRDT/consensus + conflict merge semantics         | None, but no failure motion                   |
| Fail-closed consistency     | Total (mirrors controller-fence)                     | None — conflicts "solve themselves" is the bug    | Total inside shard                            |
| Fleet precedent             | controller-fence, W643 tokens, knowledge-plane rule  | W362 peer propagation (read-only mirror only)     | hub profiles (nas/desktop today)              |

**Decision: A, with C's static binding as the default assignment and A's
handoff verbs as the mobility mechanism.** Rationale:

- The knowledge-plane adjudication (fact `adjudication.c71-73-knowledge`)
  already ruled ONE WRITER PER PROJECT, epoch-fenced transfer, NO automatic
  CRDT. Option B would weaken exactly the guard controller-fence refuses to
  weaken (cross-host takeover while liveness unknown → standby, fail-closed).
- "Never assume offline multiwriter conflicts solve themselves": under A they
  cannot occur — a partitioned party cannot mint claims or placements (CAS
  rejects carry a superseded epoch). Under B the heal is manual conflict
  surgery on a work graph (claims, done shas, merges) — no automaton can
  resolve two `work done` events for one claim, so B is rejected.
- Smallest reliable partition = {authoritative hub}: the hub alone accepts,
  runs, proves, stores, publishes. Everything else (Mac, spokes, peer hubs)
  is an optional client degrading independently to last-known read-only.
- F (full federation of READS) remains: peer pulls stay read-only mirrors
  (W362's shape) — discovery and last-known routing, never graph mutation.

## 4. Failure model — fault matrix

Each row: injection → required behavior → proof drill. Drills become bun
test fixtures against a sandbox hub (temp project, temp store, injected
clock/spawn — the maintenance override idiom).

| #   | Fault                         | Injected by…                                     | Required behavior                                                                                                       | Proof                                        |
| --- | ----------------------------- | ------------------------------------------------ | ----------------------------------------------------------------------------------------------------------------------- | -------------------------------------------- |
| 1   | Dev-machine poweroff          | Stop Mac fleet-loop + lanes mid-run              | Hub holds dispatch (post-handoff); stall/dead-claim FSM (18.1 R3) reclaims Mac lanes; hub keeps placing                  | drill: hub closes an item, Mac lanes reclaimed |
| 2   | Hub/network loss (Mac side)   | Firewall the Mac from the hub mid-lane           | Mac degrades to client: last-known manifest, read-only graph; local lane finishes; `work done` CAS-rejects (stale epoch)  | drill: zero mutations, lane output preserved  |
| 3   | Restart midstream (hub)       | Kill hub fleet-loop mid-cycle                    | Attempt-stamps re-fire; lease lapses (ttl 3× tick); epoch bump on re-acquire (18.1 fault 4)                               | drill: single owner, task re-fired            |
| 4   | Duplicate delivery            | Replay a dispatch intent + event                 | `lane_launch_intents` + claim CAS make double-fire impossible (exists today)                                              | drill: one lane, one claim                    |
| 5   | Stale leader (heal split)     | Partition heals with two ex-authorities          | Old epoch's writes CAS-reject; stale authority stands down, emits event, never crashes                                    | drill: zero double-execution                  |
| 6   | Concurrent reconnect          | Two clients reconnect simultaneously             | Both replay read-only; store is the single writer; idempotent by event id (invariant 18.3 owns)                           | drill (18.3): no duplicate rows              |
| 7   | Credential revocation         | Revoke a lane's `bksk_` key mid-run              | Buckle gate refuses → lane pauses (existing governance); no partial publication (done needs attribution)                   | drill: paused lane, no artifacts leaked       |
| 8   | Rolling deploy                | Hub pin advances mid-work                        | Version ratchet: mismatched generation yields; evidence expires to `unproven`; in-flight lanes ride to completion          | drill: placement refuses stale-generation hub |
| 9   | Capability false-positive     | Fabricate/expire `tested` evidence               | Placement re-verifies TTL+generation before use; refuses `unproven` (fail-closed)                                          | drill: stale evidence → placement refused     |
| 10  | Hub store loss                | Corrupt governor.db on the hub                   | Cycle aborts loudly; authority fails closed; clients stay read-only; no split-brain (lease-bounded authority)              | drill: zero writes before abort (18.1 fault 3)|

## 5. Decomposition and dependency-ordered acceptance

All in packages/suspenders; no new package, no new daemon:

1. `hooks/lib/hub-supports.ts` — schema, evidence states, TTL/generation
   expiry, resolve/join predicates. Pure; clock-injected.
2. `deploy/capability-drills.ts` + `test/hub-capabilities.test.ts` — the
   drill registry, sandboxed, receipts typed; suite runs the registry.
3. fleet-loop `capability-probe` maintenance task — runs due drills per
   generation, stamps evidence, honors pause flags.
4. Manifest surface: extend `HubManifestShape` with the `supports` block
   served beside `capabilities`; `federation.ts` pull stores it under the
   unchanged last-known degradation law.
5. `work-alloc` placement axis: store-backed lane source, `hub`/`place`
   fields, `requires ⊆ supports` join, `placements` table minted with the
   claim tx; `work allocate --apply` places at the authority only.
6. Hub-side controller classes: fleet-loop `--controllers <set>` (18.1 R1's
   shape), hub install registers the hub loop; authority handoff moves
   `dispatch` hub-side. Gated behind sustained40 (18.1 §4 step 6).
7. Store artifact surface: bounded blobs + retention; git-as-artifact law
   for proof receipts. (W1124.18.3 consumes this for reconnect sync.)
8. Acceptance drill: dev-machine-off end-to-end run (R4's sequence) on a
   sandbox hub — the DONE definition as a test fixture.

Dependency order: 1 → 2 → 3 → 4 (advertise truth), 5 → 6 (place + execute),
7 → 8 (prove end-to-end). Each step lands with its drill before the next.
Implementation items mint from this §5 only after review and only after the
sustained40 gate opens (same gate as 18.1).

## 6. Alternatives considered

- **A second scheduler (placement service)**: rejected — W1124.18's law is
  one domain scheduler; a placement service duplicates work-alloc's scorer
  and creates a second truth for "where can this run".
- **Unversioned boolean flags in the manifest** (W165's shape, extended):
  rejected — no evidence, no expiry, no drill; a flag flips true and stays
  true across deploys. SUPPORTS states are generation-scoped receipts, not
  install-time booleans.
- **Container-side lanes** (agents in docker on the hub): rejected for this
  phase — agent CLIs, git identity, hook gates, and worktree performance all
  assume a host checkout; hub containers serve gateways/store/board. Revisit
  under the enterprise tier's remote-execution posture, not here.
- **Automatic multi-writer reconciliation** (CRDT/last-writer-wins on the
  work graph): rejected — adjudication.c71-73 ruled it out; two `work done`
  events for one claim is not a merge, it is evidence corruption.
- **Trust-on-first-use advertisement** (accept the manifest's claims without
  local re-verification): rejected — placement re-derives sufficiency from
  TTL + generation + state, never from a fresh-looking flag alone; the hub
  advertising and the hub proving are separated (outside-process law).
