# Fleet review — 2026-10-05

Scope: the checked-out monorepo, its shipped installer and Compose templates. This is a source and integration review, not a production penetration test or a load test. I read the supplied root AGENTS rules, root `CLAUDE.md`, package instructions, implementation, and the earlier same-day audits; findings below cite the implementation. Severity is about the present checkout. The deployment and throughput conclusions are predictions unless marked reproduced.

## Verdict

The design has a good center: one SQLite work ledger, durable events, resumable lane context, a governed LLM ingress, machine-owned configuration, and external health observers. The weakest boundary is packaging. Source imports work in the monorepo, but the installed harness and Compose hubs still assume separate repositories. A lane can therefore look healthy while its board cannot load; a hub can pull archived code; and the root repository has no running CI to catch either. Fix the executable artifact boundary before increasing lane or hub counts.

The second boundary is admission. `buckle` has scoped, hashed, revocable keys and request budgets, but dispatch deliberately falls back to belt direct when the front/admin key is unavailable. That is acceptable for a developer's explicit emergency path; it is not acceptable as an automatic path for production lanes because attribution and policy disappear exactly during a control-plane failure.

## Architecture and coordination

- **Keep the work graph as the authority.** `work_items` and `work_deps` have project-scoped composite keys/FKs; WAL, a 2 s busy timeout and foreign keys are set on open (`packages/suspenders/hooks/lib/govdb.ts:383-400`, `:471-477`). `work` takes, finishes and splits through transactions (`hooks/bin/work.ts:629`, `:996`, `:1108`). Project identity derives from Git's common directory (`hooks/lib/govdb.ts:23-35`). This is more reliable than Markdown ledgers or one JSON file per lane. The pending rekey matters: a fleet checkout and an old suspenders checkout are distinct graph identities until migration.
- **Keep the coord event log and push subscription, but bound reads.** The store owns the WebSocket subscriber set and filters by target/scope/kind (`hooks/bin/store-server.ts:46-59`, `:88-115`, `:236-249`). Durable cursor reads still exist, which is good for reconnects. `cmdPoll` loads *all* events after a cursor, filters in TypeScript, then applies a default limit of 50 (`hooks/coord/bus.ts:145-180`). One dormant lane after 100,000 events pays for 100,000 rows; ten times the lanes and event volume magnifies this. Use indexed keyset pages with an over-fetch loop until 50 matching rows, advancing the cursor only across examined rows. Preserve replay and target filtering semantics.
- **Capsules are useful handoff hints, not transaction logs.** A pause requires a matching checkpoint SHA and capsule (`hooks/coord/bus.ts:430-460`); a dead dispatch resumes the same SID with its last capsule (`scripts/dispatch-next.ts:802-817`). But `capsule set` overwrites one fact with arbitrary CLI fields and no freshness or size bound (`hooks/coord/facts.ts:66-87`). A stale capsule can mislead recovery, and a crash between an edit and checkpoint still leaves uncommitted state. Record checkpoint validity and age in dispatch output, cap capsule bytes, and require worktree/status inspection before any automatic reuse. The present brief already tells the lane to reconcile (`scripts/dispatch-next.ts:396-400`).
- **Reclaim has different safety levels.** `work reclaim all` checks transcript liveness but itself warns it can strand uncommitted state (`hooks/bin/work.ts:1181-1206`). The per-item path resets a claimed item without a liveness check (`:1213-1229`), so treat it as an operator override. The monitor requires a zombie verdict and defaults to seven days before reclaim (`hooks/bin/monitor.ts:383-402`, `:571-604`); this favors safety but can block capacity for a week. At 10x lanes, separate "dead confirmed, safe to retry" from "possibly alive, needs arbitration" and make the grace period operationally visible. Never shorten it merely to improve throughput.
- **The single SQL store is an intentional serialization point.** `POST /rpc` accepts statement-shaped SQL; one connection serializes requests and a second handles remote `BEGIN IMMEDIATE` windows with a 10 s idle timeout (`hooks/bin/store-server.ts:1-13`, `:37-44`, `:150-224`). This preserves existing CLI semantics but makes one process, one write lock and the network round trips the throughput ceiling. At 10x hubs, benchmark p95 claim, event-write and board-read latency under concurrent clients. Then replace remote arbitrary SQL with narrow operations only if measurements justify it. Do not add another distributed database before this evidence.

## Reliability at 10x lanes and hubs

1. **Liveness detection will consume coordinator time.** `laneAlive` can invoke `ps` per lane and `lsof` plus another `ps` for each worktree (`hooks/lib/lane-liveness.ts:41-76`, `:79-88`). The CLI maps it over every lane (`hooks/bin/work.ts:1154-1172`). This is roughly O(lanes × process enumeration) per audit, and transcript freshness scans the projects tree for each foreign SID (`hooks/lib/lane-liveness.ts:18-39`). Capture one process/worktree snapshot per audit and index by PID/SID; make heartbeats the primary remote signal with transcript inspection as corroboration. Measure before changing the death rule.
2. **The one-second board poll can become a read amplifier.** The board advertises 1 s polling (`hooks/bin/fleet-board.ts:1-9`, `:111`). Even with WAL, many viewers and a growing event log add reads to the same host where claims and coord writes must progress. Use bounded event pages and a push/delta feed for active panels; retain explicit refresh for historical views.
3. **Sidecars are the right health boundary, with a narrow guarantee.** The probe performs a network request before serving, uses timeouts, a bounded result ring, consecutive misses and an active confirmation before down (`deploy/healthcheck/probe.ts:132-149`, `:152-223`, `:243-249`). Compose checks the sidecar port (`deploy/hub-compose.yaml:77-97`). This proves the target answered a probe; it does not prove a lane can mint a key, load installed board modules, or finish a transaction. Add those as separate synthetic readiness checks, not as more self-reported server health.
4. **Hub fan-out multiplies release risk.** `hubctl` renders a common `version` into three refs (`deploy/hubctl.ts:58-64`, `:90-125`), a sound invariant. Compose still uses three independent Git clone volumes and `main` defaults (`deploy/hub-compose.yaml:25-39`, `:99-109`, `:198-207`). Ten hubs can be on ten different effective commits after a partial pull or default fallback. Render one immutable fleet ref, fetch it once per hub, validate the ref and artifact paths, then promote only after all service probes pass. Keep a previous ref for rollback.

## Security and governance

- **Strong primitives exist.** Buckle mints `bksk_` keys once and stores only SHA-256 hashes; revocation is checked on lookup (`packages/buckle/src/gov/keys.ts:47-75`, `:97-119`). Its gate checks bearer, scopes and budgets and audits denials (`src/gov/middleware.ts:1-7`, `:71-85`, `:87-126`). The board guards reads by Host/Origin and writes with a random 0600 token (`packages/suspenders/hooks/lib/host-guard.ts:1-12`, `:39-57`; `hooks/bin/fleet-board.ts:88-107`). Root key minting runs on the hub with `umask 077` and does not print material (`deploy/hubctl.ts:146-175`). Preserve these contracts.
- **Remove automatic ungoverned lane fallback.** Dispatch mints a proxy-only key for `/w/<sid>` (`packages/suspenders/scripts/lib/lane-auth.ts:36-71`), but if the admin key is missing, it routes the lane belt direct (`scripts/dispatch-next.ts:680-695`). Make production dispatch fail closed and surface a repair action; reserve direct routing for an explicit, audited operator override. Otherwise the scope, revocation, usage and budget promises apply only when the gateway is healthy.
- **Key lifecycle is incomplete.** The lane settings file contains `ANTHROPIC_AUTH_TOKEN`, gets mode 0600, and is written on each dispatch (`scripts/dispatch-next.ts:708-733`). I found minting but no matching revoke or settings-file cleanup in the dispatch path (`scripts/lib/lane-auth.ts:36-71`; `scripts/dispatch-next.ts:762-775`). At 10x lanes, this leaves many valid keys and local bearer copies unless another, unverified sweeper removes them. Give lane keys a short explicit expiry, revoke on terminal lane state, and clean the file after process exit while retaining only key IDs for audit.
- **Do not promote the SQL store as a security boundary.** It executes client-supplied SQL (`hooks/bin/store-server.ts:150-161`) and the shared token is optional (`:26-30`, `:269-273`); WebSocket auth can put that token in a URL query (`:236-249`). It binds loopback in this implementation (`:231-234`), which is its current protection. If hub access requires a tunnel or reverse proxy, authenticate that transport, require the token, and avoid URL tokens. A compromised lane with store access is effectively a database administrator, regardless of its buckle key scope.
- **Budgets are admission estimates, not fleet-wide cost caps.** Buckle keeps counters in process, flushes deltas every 5 s, and estimates input tokens as `ceil(bodyBytes/4)` (`packages/buckle/src/gov/budgets.ts:1-6`, `:66-80`, `:91-123`, `:155-167`). Multiple gateways can each admit up to a limit; a crash before flush loses pending counts. Use a shared atomic reservation or per-gateway allocated quota before presenting these as hard cross-hub ceilings. Report actual provider usage and currency spend separately.
- **Config-over-code still leaks operational assumptions.** The hub template defaults to archived repositories (`deploy/hub-compose.yaml:37`, `:107`, `:205`); the umbrella installer also clones old sources (`packages/speedy/bin/install-fleet.ts:46-47`, `:219-226`, `:373-374`). These are not secret leaks, but they make the claimed single version false. The hard-coded home fallback in `packages/belt/bin/gateway.ts:11` should be removed so an unset HOME fails clearly.

## Cost and routing

The stack has several routing seams: belt's gateway/config and registry, buckle's policy and governance, and the extracted `local-llm` router/registry (`packages/belt/bin/gateway-config.ts:76-109`; `packages/belt/bin/registry.ts:1-2`; `packages/local-llm/registry.ts:1-2`; `packages/local-llm/router-shim.ts:3-10`). This is understandable during extraction, but it creates competing answers to "which model is resident, available and allowed?" at 10x hubs. Define one runtime model inventory and one operator-owned routing policy; make belt publish liveness/capacity, buckle enforce identity and cloud permission, and local-llm own only model process lifecycle. Do not copy policy tables between them.

The benchmark is unusually candid: it labels electricity unmetered, quality samples weak at n=33, and says code/reasoning should remain on cloud where local quality was worse (`benchmarks.md:10`, `:43-45`, `:61-83`). Keep the speed-first dispatch default stated in `packages/belt/CLAUDE.md:9-14`. Cheap local inference is valuable for bounded extraction, classification and prompt preparation; it is not a blanket substitute for coding agents. Add per-task outcomes, queue time, cold-start time, provider token cost and model energy estimates before changing the default. The current routing and fallback choices may save API spend while increasing elapsed time or rework; the table does not establish net fleet savings.

## What I would delete

1. **Delete the three repo sidecars and three legacy source defaults after the fleet artifact is bootable.** One pinned fleet checkout/volume per hub is simpler than independently cloning buckle, suspenders and belt (`deploy/hub-compose.yaml:25-39`, `:99-109`, `:198-207`). Do this as one conversion with working directories, commands, secrets and rollback tests; changing URLs alone breaks paths.
2. **Delete the old-repo acquisition path in speedy.** The umbrella installer should install from its current pinned fleet artifact, rather than shallow-cloning archived suspenders/local or treating buckle as a separate clone (`packages/speedy/bin/install-fleet.ts:46-47`, `:140`, `:219-226`, `:266-278`, `:373-374`). Keep optional layers, but make failures visible in the final status.
3. **Delete duplicate model registry/router ownership after proving the replacement.** Belt and `local-llm` both claim a "single source of truth" registry (`packages/belt/bin/registry.ts:1-2`; `packages/local-llm/registry.ts:1-2`). Keep one published inventory and remove the stale one; retire the old `local-llm/router-shim.ts` if buckle/belt already handle every supported client path. Do not delete it before a wire-level parity test.
4. **Delete obsolete pages/examples and duplicate doctrine only after links and installed consumers are checked.** The package AGENTS/CLAUDE files repeat protocols while the root lacks an on-disk AGENTS file (supplied for this review). `packages/suspenders/pages/` still exists beside the board. Put the stack laws in one source and retain short package exceptions. This is maintenance cleanup, below runtime work.

## Developer experience and verification boundary

The root README already warns that checkout and installed stack have different guarantees (`README.md:28-30`, `:147-171`) and names the migration work (`:245-254`). That honesty helps. The actual developer path still requires knowledge of package-local locks, PATH shims and old installed state; `install.sh` writes `dispatch` as a shim to the source checkout instead of the installed prefix (`packages/suspenders/install.sh:69-79`). A clean machine or moved checkout therefore breaks a command that appeared installed. Make install output show the exact executable and artifact versions, and add a post-install doctor that resolves `work`, `coord`, `dispatch`, board imports and gateway auth from their final locations.

Root `.qlty/` exists (`.qlty/qlty.toml:14-18`), so the documented on-write quality gate can run, but root CI is needed to enforce it. The UI law says Lit/no `innerHTML`; the board still assigns `innerHTML` in its shared render helper and task renderer (`packages/suspenders/hooks/board-html/core.ts:34`, `tasks.ts:82`). This is a migration debt and browser-test target, not proof of an exploitable XSS by itself. Do not claim the UI law is fully implemented until those paths are retired.

I did not deploy to a hub, use live credentials, run a 10x load test, or repeat the prior temporary-HOME installer reproduction. The claims about scaling and key accumulation are source-based risks. The installed BLAM failure is cited as a prior same-day reproduction and independently supported by the current copy/import paths. No source files were changed for this review.
